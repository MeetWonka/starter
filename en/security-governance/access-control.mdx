WonkaChat combines two layers of access control: **sharing**, where any user shares their own agents, prompts and skills with chosen people, and **administration**, where organization owners manage groups, tool access and audit the result.

## Organization roles

<CardGroup cols={2}>
<Card title="User" icon="user">
Creates personal agents, prompts and skills. Can share them with other users or groups if the organization allows it. Uses agents and skills shared with them.
</Card>

<Card title="Admin" icon="user-shield">
Everything a user can do, plus organization-wide administration: Groups, Tool policies, per-feature permissions, and the RBAC audit log.
</Card>
</CardGroup>

<Note>
Only the organization **owner** can access **User Management**. Other admins manage groups, tool policies and permissions, but not the user list itself.
</Note>

## Sharing agents, prompts and skills

Any user can share what they create — an agent, a prompt or a skill — directly from its settings, without needing an admin.

<Steps>
<Step title="Open the item's sharing settings">
From the agent, prompt or skill you own, open **Share**.
</Step>

<Step title="Choose who to share with">
Share with specific users, with a group, or with everyone in your organization (if your administrator allows organization-wide sharing).
</Step>

<Step title="Set the permission level">
Assign **Viewer**, **Editor** or **Owner** to each person or group you share with.
</Step>
</Steps>

### Permission levels

<AccordionGroup>
<Accordion title="Viewer" icon="eye">
Can use the agent, prompt or skill in conversations. Cannot change its configuration or share it further.
</Accordion>

<Accordion title="Editor" icon="pen-to-square">
Can use it and modify its configuration — instructions, tools, knowledge. Changes apply for everyone it's shared with. Cannot re-share it or delete it.
</Accordion>

<Accordion title="Owner" icon="crown">
Full control: use, edit, share with others, transfer ownership, or delete. The creator is Owner by default.
</Accordion>
</AccordionGroup>

<Tip>
Give most people Viewer access. Reserve Editor for collaborators who should be able to change behavior for everyone, and Owner for whoever is responsible for the item long-term.
</Tip>

## What administrators manage

Administrators configure organization-wide access from **Settings → Organization**.

<CardGroup cols={2}>
<Card title="Groups" icon="people-group" href="/en/administration/groups-and-tool-policies">
Organize users into groups so you can share agents, prompts and skills, and grant connector access, to a whole team at once.
</Card>

<Card title="Tool policies" icon="toggle-on" href="/en/administration/groups-and-tool-policies">
Allow or deny specific connectors (MCP servers) per user or group — for example, letting only a team use a CRM connector.
</Card>

<Card title="Per-feature permissions" icon="sliders">
Control, organization-wide, who can create or share agents, prompts, skills and memories — for example, restricting agent creation to a subset of users.
</Card>

<Card title="RBAC audit log" icon="file-lines" href="/en/administration/audit-log">
A record of every permission change: tool policies, groups, role changes and connector access, for accountability and review.
</Card>
</CardGroup>

<Info>
Single sign-on, two-factor authentication and organization settings are covered in [SSO and 2FA](/en/administration/sso-and-2fa) and [Organization settings](/en/administration/organization-settings).
</Info>

## Restricting what an agent's tools can do

When you build an agent and add a connector (for example Outlook or a CRM), you can enable only the specific actions it needs and leave the rest off.

<Tabs>
<Tab title="Example: drafting only">
Keep **read emails** and **draft email**, and leave **send email** and **delete email** off. The agent can prepare a draft for you to review, but cannot send or delete anything — the capability doesn't exist for it.
</Tab>
<Tab title="Why this matters">
An agent only has the actions you explicitly enable. Removing an action for an agent is a stronger guarantee than instructing it not to use it.
</Tab>
</Tabs>

<Warning>
When a shared agent uses a connector, it acts with **the current user's own permissions** in that tool — not the creator's. Review what data different users of a shared agent can reach before sharing widely.
</Warning>

## Good practices

<CardGroup cols={2}>
<Card title="Limit admins" icon="user-shield">
Keep the number of administrators small. Most people only need to create and share their own agents.
</Card>

<Card title="Share narrowly first" icon="user-lock">
Share with the specific users or group who need it before sharing with the whole organization.
</Card>

<Card title="Review the audit log" icon="calendar-check">
Periodically check the RBAC audit log for unexpected permission or tool-policy changes.
</Card>

<Card title="Match tools to purpose" icon="wrench">
Enable only the connector actions an agent needs for its task, nothing more.
</Card>
</CardGroup>
